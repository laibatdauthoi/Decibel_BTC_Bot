# Production order decision pipeline audit

This is an application code audit and deterministic replay, not a deployment or a claim about current mainnet state. No live orders, session starts, cancellations, restarts or production journal writes were performed. Existing uncommitted recovery, TP, defensive-exit and UI changes are preserved.

## Findings and changes

1. **Contradictory final preflight inputs.** `run_decibel_production_web_v1.validateSubmission` forced a fresh authenticated snapshot, recomputed authorization and sizing, and validated exact order limits. `decibel_execution_lifecycle_v1.submit` then validated the same order against the planning-time `input.preflight`. The second limit set could still include an old reserved order or a smaller old order cap. This is a proven data-flow defect: a permissive fresh admission could be defeated by stale planning limits. The fresh hook now returns one complete limit set, carried through the live orchestrator, and the lifecycle performs the final exact-order validation once using that set. Hooks returning void retain the previous fallback. Exclusive ownership is still checked after the refresh; the journal claim, side ownership, mutation budget, exact quantity, risk, maker, unit and exposure checks remain.
2. **Necessary block reasons were discarded.** All-blocked action selection could become `KEEP:ADMISSION_BLOCKED`; failed final authorization, frozen replacement/commit revalidation and some post-cancel guards could return HOLD. These branches now return BLOCKED with their actual existing reason. Genuine strategy KEEP and no-action states remain unchanged. SDK known rejections retain PLACE_REJECTED/CANCEL_REJECTED. Unknown submission outcomes remain reconciliation work, never an authorization to retry.
3. **Missing final decision provenance.** Each cycle now includes `INTENDED_ACTION`, `FIRST_BLOCKING_GATE`, `REQUIRED_EVIDENCE`, `ACTUAL_CAPACITY_LIMIT`, and `FINAL_EXECUTOR_OUTCOME`. These are observational fields; they add no gates, settings or retries. The capacity record distinguishes planning facts from the final validation clock/limits. A successful acknowledgment has a null blocking gate. Missing cycle results are UNKNOWN unless an actual cycle error exists.

These defects are established in source and composed executor tests. The exact competing final/planning limit sets were not persisted for the supplied production PIDs. Therefore the new preflight fix cannot honestly be attributed as the cause of every historical stall.

## Actual pipeline and authoritative evidence

`readAuthenticatedSnapshot` assembles normalized account position, residual open orders and authenticated fill/terminal history. `mergeDecibelVenueReconciliationSnapshotV1` checks source windows, identity and ordering; publication does not give old observations a new freshness clock. Account margin and venue risk inputs feed `calculateDecibelRiskCapacityV1`, then `deriveDecibelSessionTradingLimitsV1` and `calculateDecibelDynamicQuoteSizeV1`.

`evaluateDecibelAuthenticatedPassiveRecyclingV1` and the smart ladder produce strategy candidates; `evaluateTradingDecision` governs action-specific evidence and canonical risk reduction. `selectMutation` compares resting orders with candidates, including economic replacement rules. A selected replacement first cancels the exact owned order; cancellation acknowledgment alone is not proof of terminality. The frozen plan is recreated only after authoritative reconciliation and quantity/position revalidation.

Immediately before submission, the web source asserts the session owner, refreshes/project venue evidence, reevaluates the candidate and returns final limits. The lifecycle claims the intent, enforces journal ownership and mutation budget, validates exact preflight and calls the gated executor. The executor validates identity, release mode and wire order invariants. ACK is followed by authenticated reconciliation; timeout/unknown remains journal-owned pending evidence. A missing order in one snapshot does not prove cancellation or a failed submission.

## Why apparent capital does not imply authorization

The current model computes position margin as `abs(position) * mid / effectiveLeverage` and conservatively reserves open-order margin as `sum(price * remainingQuantity) / effectiveLeverage`. Usable margin is the smaller of authenticated venue free margin and `max(0, CapitalToUse - marginUsed)`. Strategy headroom also accounts for current/pending exposure and the risk-capacity certificate. Dynamic sizing then takes the minimum of strategy proposal, position headroom, margin-funded notional, per-order cap and remaining volume, floors to lot size and enforces executable minimums. Replacing-order credit applies only to the explicitly replaced reservation.

PID 18996 fixture: available margin USD 6.18759135 at 40x gives USD 247.503654 gross margin-funded notional before explicit replacement credit. The strategy headroom is only USD 57.2151725 and maximum order notional USD 114.430345; more free margin cannot enlarge those limits. BUY resting 80318.3 x 0.00019 and SELL resting 80613.9 x 0.00071 remain exposure/reservation evidence. BUY candidate 80520.2 x 0.00071 is USD 57.169342; SELL candidate 80681.5 x 0.00070 is USD 56.47705. Even executable sizing does not prove replacing the old order is beneficial. The BUY comparative adverse-selection sample is 22/30 and the resting depth lacks supported evidence; SELL's farther-away quote does not establish improvement. Both remain KEEP in the exact fixture.

A reduce-only exit cannot be treated as a new entry allocation. Existing canonical reduction and same-price TP repair paths remain intact, with exact current position/remaining quantity limits. This audit did not authorize changing any residual margin/volume policy or prove a new defect in those formulas.

## Verification and limitations

- Focused historical/execution/recovery run: **420 passed across five files** (320 live orchestrator, 33 lifecycle, 50 lifecycle recovery, 11 authoritative reconciliation, six HTTP recovery).
- Full `npm test`: **877 passed, two failed** in the production-core stage. Both failures are Chromium presentation tests: Chrome GPU subprocess/access-denied failures. The subsequent command chained with `&&` was skipped; its authoritative/HTTP tests passed in the focused run.
- `npm run typecheck` and `npm run build`: passed.
- Changed-source ESLint: passed. Global `npm run lint`: blocked by preexisting project-service parse errors in `.tmp_conflict_readonly.cjs` and `.tmp_exact_evidence.ts`.
- Global `npm run format:check`: preexisting `.tmp_conflict_readonly.cjs` fails formatting. Changed files are checked separately.

No current authenticated venue read was required for this code-only audit and no current position/order claim is made. Historical production logs do not contain both competing final limit sets, so incident-specific causal attribution remains unestablished. Tests demonstrate the precise application failure mechanisms and the final fake executor outcome; they do not demonstrate mainnet deployment or live recovery.
