# PID 24500 Start Admission Fix

EXACT_RACE_OR_REJECTION_ROOT_CAUSE= The first recorded request did not reject before all venue reads completed. It requested at 1793298606909 with the previous observation 1793298601878 (age 5031ms). During that request, ACCOUNT_OVERVIEW, POSITIONS, OPEN_ORDERS, ACCOUNT_RISK_INPUTS and VENUE_MARGIN_RULES succeeded. At rejection (1793298618814), the newer account observation was 1793298613656, already 5158ms old; refreshInFlight was false. Thus fresh evidence was obtained during the request, but aged through local publication/admission work. The previous admission path made a refresh and then another conditional refresh/readiness assertion; it could exhaust both reads' freshness before admission. It also retained the first admissionSnapshot when the second refresh supplied newer evidence.

A demonstrated source of local TTL consumption was repeated journal scans in reconcileDecibelAcknowledgedTerminalOrdersV1: every historical cancelled venue order performed getOrderLineageByVenueOrderId, and each query scanned execution_intents without an index. A read-only benchmark on 160 production venue identities took 8242ms for the individual queries versus 118ms for one batch, with identical 256 returned rows. No index/schema or production journal modification was made. This demonstrates the scan amplification; it does not claim a retrospective profiler measured every millisecond of the rejected request.

START_REFRESH_SINGLEFLIGHT_BEHAVIOR= Existing RuntimeSupervisor.runAuthenticatedRefresh already shares one promise and bounds its venue operation. The rejected request began with no refresh in flight and started a read; another recorded request began with refreshInFlight=true and joined the owner. Publication was inside the shared operation, so this is not a missing await on the HTTP promise. The fix removes the split read/check path: one explicit Start owns a bounded refresh-and-validate workflow, always calling the shared refresh, awaiting publication, and consuming that refresh's venueSnapshot rather than a mutable global projection. After reconciliation, capital, account/order and ownership/recovery dependencies are evaluated again. The original evidence clock is checked before and after validation; a newer background snapshot cannot silently make an older validation fresh. Only successful evidence that ages during local work permits another read/validation pass (maximum three passes within the existing configured readTimeoutMs). Actual HTTP/source/validation errors reject immediately. A workflow timeout is terminal; late shared publication cannot admit that request.

BEFORE_AFTER_EXACT_PID24500_REPLAY= Deterministic tests replay the production epochs and 5158ms age: ENDED/stale -> REQUESTED -> STARTING -> successful publication aged past TTL -> REJECTED -> later publication -> WAITING_FOR_USER_START/NONE. The after replay uses the same starting stale observation and original evidence clocks, batch-publication cost, shared refresh and real session controller against temporary test storage: the original explicit request creates one RUNNING session and activates once. A separate test crosses TTL during validation while background evidence becomes fresh, proving validation repeats using the new coherent result rather than admitting the old decision. Failure/deadline tests prove later publication does not auto-start after a terminal rejection.

READINESS_NONE following the rejected request reflects subsequently available evidence, independently of the historical rejection. Forensics proves the account observation 1793298613656 was obtained during the rejected request and was stale by its rejection; a later readiness NONE cannot retroactively authorize that request. The next separately recorded explicit request at 1793298713495 began with refreshInFlight=true and was admitted at 1793298728657. This pre-existing record was read from process_forensics.jsonl; no Start was sent by this investigation. Post-rejection publication epochs are not preserved in the old periodic readiness log, so exact attribution of the first NONE to a particular later read remains unavailable.

REAL_HTTP_FAILURE_VS_LOCAL_STALE_DECISION= For the supplied rejection, recorded source stages succeeded; the terminal result was a local stale-evidence assertion. HTTP 500 and timeout paths remain failures with their original stage/cause. Tests cover failures, no automatic retry/admission after terminal failure, fresh background recovery with no session creation, and a later explicit successful request. Genuine unavailable/stale evidence remains fail-closed; neither TTL nor timestamps are rewritten.
